# Source access and agent authority boundaries

The first end-to-end scenario reads public web information. Future integrations are evaluated per application and function, with official APIs or supported connectors considered first and alternatives assessed when they cannot meet the function's needs. The source's API grant or authenticated session sets the technical access ceiling; each function selects the data and tools it uses within that ceiling, while separate per-function execution permissions govern autonomous operations and unconfigured operations require user approval. Plugins and MCP tools receive only the operations and data needed for the current function. Explicitly prohibited access methods are excluded unless the platform grants written permission; unclear methods remain disabled pending app- and function-specific technical, security, and platform-rule review, which cannot guarantee that an account will never be restricted. This decision is recorded in [Choose the inbound source strategy and account-access boundary](https://github.com/clementineyyy/pi/issues/4), informed by [the access-path research](https://github.com/clementineyyy/pi/issues/5), [Alipay's service agreement](https://cschannel.alipay.com/mobile/helpDetail.htm?flag=0&help_id=201602698273), and [Taobao Open Platform's security rules](https://developer.alibaba.com/docs/doc.htm?articleId=105704&docType=1). Shared persistence and source-data retention remain undecided in [Choose persistence boundaries for agent state and connected-source data](https://github.com/clementineyyy/pi/issues/9).
